# Malachite rc.3 Fork Reconciliation Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or
> superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Produce a reviewed 1Money Malachite fork commit reconciled through Circle v0.6.0-rc.3 while preserving
Emerald-required ECDSA, WAL, value-sync, failure-reporting, and diagnostic behavior.

**Architecture:** Add production-baseline compatibility fixtures and downstream characterization tests before merging
the exact rc.3 commit into the current fork. Resolve the merge by behavior, retain the current fork's queue model and
ECDSA surface, and leave Emerald-specific codecs, redb state, pinning, and rollout qualification to the linked
follow-up.

**Tech Stack:** Rust 1.85, Cargo workspace, Tokio, ractor, libp2p, prost, redb, ECDSA (`k256`, `p256`, `p384`),
`cargo-nextest`, Git merge ancestry.

**Spec:** `docs/superpowers/specs/2026-11-04-reconcile-fork-through-rc3-design.md`

- Preserve `batch_size * parallel_requests` as the combined inflight and pending-consensus height allowance.
- Preserve response-size limits, restored-height startup gating, stale-prefix trimming, and honest late-reply handling.
- Do not delete/reset WAL state, rewrite signed history, or treat a successful build as compatibility evidence.

- Malachite remains generic. Emerald codecs, addresses, redb data, and deployment work stay in Emerald.

- Keep Markdown at or below 120 columns.

## Review Focus

- A fixture regenerated by the candidate could bless an incompatibility; Tasks 2 and 3 pin source commits and exact
  fixture bytes generated at `bcac2b2d` and `eb2405ba`.
- A truncated or corrupt production WAL must fail explicitly rather than replay a prefix; Task 3 adds corrupt/truncated
  fixture tests.
- Unknown, wrong-peer, delayed, and stale sync replies must not consume or release the wrong capacity; Task 4 adds
  state-level regressions for each class.
- A response exactly at the configured byte limit must be accepted while the first value beyond it is excluded; Task
  4 pins both boundaries.
- Closed, full, and dropped-response consensus request channels must remain distinct failures; Task 6 tests all three
  `ConsensusRequestError` variants.
